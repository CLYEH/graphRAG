# 使用方式(step 8 / prep 協定)

- **即時狀態**(PR、任務、額度)一律查 `TASKS.md` 與 GitHub;本檔只留跨任務可重用的教訓。
- **開工前(prep)**:按任務型別讀命中的 class(各 class 開頭有「何時比對」)。教訓存在≠教訓被套用——catalog 是開工前讀物,不是事後對照(#74 以身試法:class 17 原文預言了那顆 bug,我照樣寫了事件計數器)。接手他人/舊 session 的主張先查證再動工,一半是過時的(#87);接手 stale summary 時以 repo 現況為準(#67)。
- **step 8 retro**:每個 finding 先比對 class 目錄──命中=在該 class 追加一行 sub-point(附 PR 錨點);未命中=開新 class(**編號穩定,只增不改號**)。**不再寫 per-PR 敘事段**(2026-07-20 裁剪定案);輪次經濟學、任務史、路線圖一律不進本檔。新 class 若可機械化,**優先立 H-task 做成 hook/CI/lint/共用 helper**(mechanize-first,owner 2026-07-20 方向),prose 是最後手段。
- 每個 class 標注機械化狀態:`[已機械化:<機制>]`／`[可機械化→H<n>]`／`[pattern]`(可抽共用 helper/測試模板)／`[prose]`(不可約簡的判斷)。

- **S14 腳本化的字串替換要有界——無界 replace 是污染源,不是省事**(#146)。改一支測試檔的詞彙時我用了「從某位置起把 `"approved"` 全換成 `"accepted"`」,它掃過了目標,污染了**同檔中不相干的 entity review 測試**——`review_status` 是 `unreviewed|approved|rejected`,與 ontology-proposal 的 `proposed|accepted|rejected` 是**兩套詞彙**,被換成一個該路徑永遠不可能產生的值;測試照樣綠,因為 stub 原封回吐你餵的東西,而兩行上的註解仍寫著 approved。gate-2 抓到才知道。判準:**替換前先數命中數,替換後 `git diff` 逐 hunk 看過**;跨越「我要改的那個測試」邊界的替換,一律改成逐處具名替換。同源提醒:綠燈不是替換正確的證據——stub 回吐型測試對值的**語意**是盲的。
- **S11 本機 integration 紅燈先診斷再重跑**:紅燈會把人推去懷疑自己的 diff,但成因常在環境(#142:殘留 arq build worker 與測試搶 build、逾時的背景 `check-full` 與新一輪並跑導致 migration 測試 downgrade schema 時另一輪正在查(`entities.disambiguator does not exist`)、強殺留下鎖造成 teardown deadlock)。定案方法=**在 clean main 上 baseline**(stash 後同一套件照樣紅=非本 diff)+ 確認失敗檔對改動處零引用 + 單獨跑會過;CI(全新容器)為權威。紀律:同時只跑一個 integration;跑前停 arq worker;背景 gate 逾時就先殺再開下一輪。
- **S9 額度逃生閥**:Codex 額度用盡且 gates 全綠+小幅已驗證 delta 時,由 **owner 本人**決定是否親自 merge——是 owner 決策,不是 agent 例外。
